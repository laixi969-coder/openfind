# 数据备份、恢复与迁移检查

## 确认并修复的问题

1. 原先只有手动备份说明，复制 SQLite 主文件可能漏掉 WAL 中最新记录，且容易漏掉 uploads 或密钥。新增 `data:backup` / `data:restore` 命令，使用 `VACUUM INTO` 生成一致性数据库快照，并配套素材、密钥、版本化清单和 SHA-256 校验。
2. 数据库存在但密钥遗失时，启动原先生成替代密钥，旧加密凭证无法恢复。现在在生成密钥前拒绝启动，并提示恢复原密钥；损坏长度也明确拒绝。
3. 旧服务配置迁移原先只要存在任意服务就全部跳过，导致另一类服务漏迁移。现在按类型迁移，在同一 SQLite 事务中保存记录、活动服务和迁移标记。重复迁移不覆盖已有服务、不复活已删除服务。

## 一致性约束

- 建议停机执行完整备份，避免同时修改或手工删除素材；数据库快照本身覆盖 WAL。
- 备份或恢复时检查 SQLite 完整性、配置表、实体 JSON、本地素材路径及存在性、已知凭证能否由同包密钥解密。
- 备份清单包含数据库、密钥和素材的内容摘要；恢复拒绝路径穿越、不支持的清单版本、文件篡改、缺失文件和已有目标目录。
- 在同级临时目录完成检查后再重命名发布；失败清理临时目录，不覆盖现有数据。
- 旧数据不要求新增 revision 字段，沿用应用读取时的默认版本兼容逻辑。SQLite 未版本化旧库（user_version=0）保持兼容，未来版本号明确拒绝盲目降级。

## 验证

`tests/data-backup.test.ts` 覆盖活跃 WAL 的数据库快照、配置和凭证完整恢复、独立进程启动、素材恢复、缺失素材失败、篡改失败、禁止覆盖目标、密钥丢失时不生成新密钥，以及部分旧服务迁移和重复迁移。

浏览器 profile 和内存临时凭证不在成套备份范围；浏览器登录状态依赖 Chrome/操作系统，恢复后需重新登录。备份不是加密归档，含密钥，必须妥善保管。此轮未操作用户的实际业务数据目录，也未自动提交或推送代码。
